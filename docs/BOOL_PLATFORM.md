# BOOL — מה נבנה ומה צריך מכם

מסמך זה מתאר את שדרוג rocca-social-bot לפלטפורמת BOOL. הקוד כולל בדיקות אוטומטיות (`npm run platform-check`, `platform-unit`, `tenant-check`, `tenant-unit`, `smoke`, `ui-check`).

## מה עובד
| רכיב | מצב |
|---|---|
| רב-לקוחות (נתונים נפרדים לכל עסק) | עובד, נבדק מול קבצים ו-Postgres |
| Freemium: 3 פעולות במתנה, בלי כרטיס | עובד. הרשמה → `free_trial` עם 3 קרדיטים |
| קרדיטים (`checkCredits`) | עובד. פעולת AI מוצלחת = קרדיט; נגמר → 402 עם הפניה לשדרוג. חבילות עסקים ללא מגבלת קרדיטים (תקרת עלות חודשית נשארת) |
| מסלולים | free_trial, creator_lite/pro, starter_social, digital_core/pro, total_dominance (+ basic/premium/vip הישנים) |
| חסימות | טייס אוטומטי: מ-creator_lite. דומיין עצמאי: מ-digital_core. תקציב ממומן: digital_pro+ |
| קרוסלה (כמה תמונות) | פייסבוק (אלבום) ואינסטגרם (קרוסלה עד 10). נבדק מול מוק של Graph API — **לא נבדק מול Meta חי** |

| סליקה | מסך אישור + הזמנות + קישור תשלום לכל מוצר + webhook; הפעלה ידנית בטאב ניהול (ראו למטה) |
| חלוקת תקציב חכמה | מחשבת חלוקה שבועית לפי עלות לפנייה/קליק, עם הסבר בעברית |
| אתר + SEO | אתר קטן ב-`/s/<key>`, מאמרי SEO, מפת אתר, קרדיט "Powered by BOOL" (ניתן להסתרה בחבילות גבוהות) |
| תמיכה | צ'אט AI + פניות לצוות (טאב "ניהול") |
| דומיינים | `boolai.co.il` → אתר שיווקי, `app.` → דשבורד, `api.` → API בלבד; CORS לדומיינים של BOOL/ROCCA |

## מה לא נבנה / מה שונה מהמפרט (בכוונה)
1. **מיגרציית SQL (`002_bool_platform_setup.sql`) לא נכתבה.** המערכת שומרת נתונים כמסמכים (טבלת `documents` יחידה ב-Neon), לא בטבלאות `users/posts`. כל השדות שביקשתם (tier, credits_balance, commitment_months, subscription_cycle, country, city, currency, language, autopilot_enabled, ad_budget_monthly, ad_auto_distribute, ad_platforms_enabled; leads; campaign_logs_and_insights; client_websites; support_tickets) קיימים כמסמכים לכל עסק. מעבר לטבלאות יחסיות הוא פרויקט נפרד.
2. **ROCCA הוא כבר ה-Seed Tenant** (החשבון הראשי): ללא שינוי בנתונים. מסלולו `PLAN_TIER` (ברירת מחדל `total_dominance`). הטייס האוטומטי שלו כבוי עד שתדליקו אותו בלשונית "ראשי".
3. **תשלומים:** לא נבחרה חברת סליקה. לכל מוצר מגדירים `CHECKOUT_LINK_<SKU>` (עמוד תשלום מאוחסן אצל הספק) ואת `PAYMENT_WEBHOOK_SECRET`; הספק קורא ל-`POST /api/billing/webhook` עם `ref` ו-`paymentRef`. בלי זה, "לרכישה" מחזיר הודעה שהסליקה לא הוגדרה, והמפעיל יכול להפעיל חבילה ידנית בטאב "ניהול". חידוש מנוי = webhook נוסף; אם לא הגיע תוך מחזור+3 ימים, החשבון חוזר ל-free (הקרדיטים נשמרים).
4. **הוצאת כסף על מודעות:** המנוע **ממליץ** על חלוקה ומסביר; הוא לא מפעיל קמפיינים ולא מוציא כסף. זה דורש הרשאת `ads_management` ממטא (App Review) וחיבור Google Ads. הנתונים נכנסים כרגע ידנית (טופס "הזנת נתוני שבוע").
5. **טיקטוק, גוגל ובוט מענה 24/7 (Total Dominance):** לא נבנו. מסומנים "בקרוב" בקטלוג. טיקטוק/X/אתר חיצוני רצים על פרטי הגישה של המפעיל ולכן חסומים ללקוחות אחרים.
6. **דומיין עצמאי:** הלקוח מבקש, המפעיל מפנה DNS ומאשר (`POST /api/admin/sites/:id/domain/activate`). רישום דומיין ללקוח לא אוטומטי.
7. **גרפים:** חלוקת התקציב מוצגת כסרגל מוערם ולא עוגה (עוגה מקשה על השוואה).
8. **קרדיט באתרים:** "Powered by BOOL" בלבד, מקשר לאתר של BOOL (ללא קישור לרוקה: רוקה ו-BOOL הם שני עסקים נפרדים). Digital Pro ומעלה יכולים להסתיר אותו (מיתוג לבן). `BOOL_CREDIT_NOFOLLOW=true` מוסיף nofollow אם רוצים להרחיק את הקישור מגרף הקישורים של גוגל.

## מחירים, מע״מ וסליקה
- **תצוגה אחידה (Gross, ברירת מחדל `PRICE_DISPLAY=gross`):** המחיר הבולט בכל מקום (אתר, דשבורד, מסך אישור) הוא המחיר הסופי **כולל מע״מ**, ומתחתיו שורה קטנה: "מתוכם 18% מע״מ: ₪X (מחיר לפני מע״מ: ₪Y)". הקטלוג ב-`billing.ts` מוגדר לפי מחיר לפני מע״מ והסכום הסופי כולל מע״מ 18% (`VAT_RATE`) **מעוגל לשקל שלם**, והמחיר לפני מע״מ והמע״מ נגזרים ממנו, כך שמה שמוצג הוא בדיוק מה שנגבה ויופיע בחשבונית: ₪790 → ₪932; ₪1,490 → ₪1,758 (₪1,489.83 + מע״מ ₪268.17); ₪1,890 → ₪2,230; ₪2,490 → ₪2,938; ₪19 → ₪22; ₪49 → ₪58; ₪29 → ₪34; ₪69 → ₪81; ₪129 → ₪152. `PRICE_ROUNDING=agora` מחזיר סכומים מדויקים עד האגורה (₪932.20). `PRICES_VAT_NOTE` = "המחירים כוללים מע״מ כחוק". `PRICE_DISPLAY=net` מחזיר את התצוגה הישנה.
- **בעמוד התשלום של הספק מגדירים בדיוק את הסכום הסופי השלם (למשל 1,758).** אם הספק מדווח בוובהוק את הסכום שנגבה (`amount`), הוא נבדק מול ההזמנה, וסכום שונה נדחה.
- **זרימת רכישה:** מסך אישור (מחיר, מע״מ, סה״כ, תנאים ותיבת סימון) ← הזמנה ממתינה עם מחיר קפוא ← עמוד התשלום של הספק ← webhook מסמן "שולם" ומפעיל את החבילה ← חזרה לאפליקציה (`#checkout=success`) שממתינה לאישור. ההזמנות מופיעות ב"חבילות ← ההזמנות שלי". הכתובות שיוגדרו אצל הספק כחזרה: `https://app.boolai.co.il/#checkout=success` ו-`#checkout=cancel`.
- **הפעלה ידנית (טאב "ניהול"):** בכל לקוח, "הפעלת חבילה ידנית…" מפעילה חבילה בלחיצה (עסקה שנסגרה בשטח / דרך חנות / העברה), עם הערה, ונרשמת כהזמנה ידנית. אפשר גם לשנות מסלול ולהוסיף קרדיטים.
- **Starter Social:** ₪790 לחודש (₪932.20 כולל מע״מ), חודשי **ללא התחייבות** (הנחה שלי; להפוך להתחייבות שנתית = `commitmentMonths: 12` ב-`billing.ts`).
- **אפליקציה בחנויות (Google Play / App Store):** המדיניות של שתי החנויות דורשת בדרך כלל חיוב דרך המערכת שלהן (IAP / Play Billing, בעמלה) על קרדיטים ומנויים דיגיטליים שנרכשים בתוך האפליקציה, ואוסרת קישור החוצה לתשלום באתר (יש חריגים לפי אזור). לכן בגרסת חנות (`window.BOOL_STORE_APP` או `?store=1`) כפתורי הרכישה מוסתרים ומוצג "את המנוי מנהלים באתר", והשרת מסרב ליצור תשלום מבקשה כזו (`X-Store-App`). הרכישה בפועל נשארת באתר, ובחנות הפעלה ידנית לעסקאות שנסגרו מחוץ לאפליקציה. אם תרצו למכור קרדיטים בתוך האפליקציה, צריך לחבר IAP לפי כללי החנויות ולבדוק אותם לפני הגשה.

## אסטרטגיית סליקה לפיילוט (עד 10 לקוחות ראשונים)
**מודל:** Merchant of Record בינלאומי, בלי סליקה ישראלית ישירה בשלב זה. ה-MoR הוא המוכר הרשמי: הוא גובה, מטפל במיסוי ומוציא קבלה/חשבונית ללקוח, והכסף נצבר ביתרה אצלו ומועבר אליכם.

**מה מחובר בקוד: Lemon Squeezy.**
- לכל מוצר: `CHECKOUT_LINK_<SKU>` (קישור checkout מ-Lemon Squeezy) + `CHECKOUT_REF_PARAM=checkout[custom][ref]`, כדי שהזיהוי החתום שלנו יעבור דרך התשלום ויחזור ב-webhook.
- ב-Lemon Squeezy מגדירים webhook לכתובת `https://api.boolai.co.il/api/billing/webhook/lemonsqueezy` עם אירועים `order_created` ו-`subscription_payment_success` וסוד חתימה (`LEMONSQUEEZY_WEBHOOK_SECRET`). האימות הוא חתימת HMAC-SHA256 על הגוף ([תיעוד](https://docs.lemonsqueezy.com/help/webhooks/signing-requests)), ולא `PAYMENT_WEBHOOK_SECRET` (שנשאר ל-webhook הכללי `/api/billing/webhook` לספקים אחרים או להפעלות אוטומטיות).
- **חובה:** `CHECKOUT_PRODUCT_<SKU>` = מזהה ה-variant של כל מוצר. השרת מפעיל חבילה רק אם המוצר ששולם הוא המוצר של ההזמנה (אחרת אפשר לשלם על החבילה הזולה ולקבל את היקרה), ואם חסר מיפוי הוא מסרב.
- חידוש מנוי (`subscription_payment_success`) מוסיף קרדיטים ומאריך את התוקף רק לחבילה שכבר נרכשה ואומתה; תשלום ראשוני לא נספר פעמיים; שליחה חוזרת של אותו webhook לא מזכה פעמיים.
- **לא נבדק מול Lemon Squeezy חי.** הנתיב נבדק עם הודעות מדומות לפי התיעוד. לפני לקוח ראשון יש להריץ רכישת בדיקה ב-Test mode ולוודא ששדות `meta.custom_data.ref`, `first_order_item.variant_id` ו-`billing_reason` מופיעים כצפוי.

**שני דברים שחייבים לאמת מול ה-MoR לפני שמוכרים:**
1. **מע״מ ישראלי:** ה-MoR מחשב מס בעצמו לפי מדינת הקונה, והסכום ומטבע החיוב נקבעים אצלו. התצוגה שלנו ("כולל מע״מ 18%") חייבת להתאים למה שהוא גובה בפועל בישראל. יש לבדוק מולו שהוא גובה מע״מ ישראלי, ולהגדיר את המוצרים בשקלים בתמחור כולל מס. אם לא, יש להתאים את התצוגה או לדבר עם רו״ח.
2. **הכנסות:** הכסף שמגיע מה-MoR הוא הכנסה שלכם מול הרשות, ולכן יש לתאם עם רו״ח איך מדווחים (חשבונית עצמית ללקוח אינה נדרשת כשה-MoR הוא המוכר, אבל הדיווח על ההכנסה כן).

**Paddle:** דורש הטמעת Paddle.js בדפדפן כדי להעביר את הזיהוי החתום (קישור checkout רגיל לא נושא אותו), ולכן לא נבנה כרגע.
**In-App Purchases (Apple / Google):** דורש אפליקציה נייטיבית (StoreKit / Play Billing) ואימות קבלות בשרת מול Apple App Store Server API ו-Google Play Developer API, עם מפתחות מחשבון המפתחים. עד שתהיה אפליקציה בחנות, גרסת החנות מסתירה כפתורי רכישה ("את המנוי מנהלים באתר"), והרכישה נשארת באתר דרך ה-MoR. חיוב דרך החנויות כרוך בעמלה של 15%–30%.

## החלטות שעדיין פתוחות אצלכם
- כמה קרדיטים בכל מנוי: הנחתי שבועי 10, לייט 40, פרו 100 (`billing.ts`).
- פתיחת חשבון Lemon Squeezy, הגדרת מוצרים בשקלים, והעברת מזהי ה-variant (`CHECKOUT_PRODUCT_<SKU>`).
